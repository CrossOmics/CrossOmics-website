# Tool discovery, personal contributions and maintenance

User screenshots request a clean Tracking System: rename search to Search Tools; homepage shows Original tools only, with later updates on Tool detail; rename personal page My Contributions and group My Tools / My Updates / My Maintained Tools; contextual Tool actions; tool-level maintainers; all versions with up to two recommended versions.

User explicitly approved: administrators assign Tool maintainers by Community Contributor ID. Assigned maintainers may edit existing Tool metadata and choose up to two published recommendations. Review, withdrawal and maintainer assignment remain administrator-only. Never derive management rights from display names, GitHub handles, registration authorship or version credits. Existing registrations and contribution records remain separate.

## Design and boundaries
- Keep the existing unified contribution entry and navigation work from frontend PR34. New work uses a separate branch based on that branch; do not merge PR34 or production deploy automatically.
- Home has Search Tools and one card per Tool with a nonwithdrawn Original version; remove the version type selector. All versions stay accessible on detail and registration forms. Legacy kind normalization still applies. Do not delete imported or withdrawn records.
- Tool detail displays public maintainers once at Tool level. Version cards retain authors/citation/change evidence, but no per-version maintainer blocks. List all versions, up to two recommended nonwithdrawn versions first with explicit Recommended badges; never label an update Original or hide history. Tool actions are Source repository, View contributions, Submit an update (Tool ID preselected), Record work on this tool (ID and record mode preselected), and Manage this tool if authorized. There is no generic duplicate Submit a Contribution button in the Tool header.
- My Contributions has paginated tabs My Tools, My Updates, My Maintained Tools. The first two combine the user's registry submissions and separately recorded contributions of the respective canonical type, with explicit record/submission labels and review status. This means submitted/recorded by this account, not proof of original authorship. Maintained shows only Tools explicitly assigned to this Community ID; administrator status alone does not populate that list. No false totals from filtering one page of all history. Keep impact editing and personal ID, sign-out, desktop access.
- Manage this tool is a dedicated protected page. Admins and assigned maintainers can edit the existing four Tool metadata lists and replace the ordered recommendation selection (0–2 versions, published, same Tool, not withdrawn). Admins can edit public Tool maintainer credits and optional Contributor ID bindings with a reason. Public display credits never expose binding IDs. Non-admin maintainers cannot grant/revoke maintainers, review or withdraw versions. The management page explains these limits and links back to Tool.
- Migration seeds global display maintainer credits from Original credits (fallback earliest legacy version only where no Original exists), without granting privileges. Existing per-version credits are retained internally for history and compatibility. New Original publication initializes Tool-level display credits; Update publication never changes Tool maintainers. Reapplying the migration must not overwrite later maintainer edits or resurrect removed credits. All management changes are audited with actor/reason/previous values.
- Permission checks use authenticated server identity and same-origin writes, reject desktop bearer credentials for management. Recheck authorization under the same Tool-level transaction lock as modifications; revocation and metadata/recommendation writes serialize. Resolve aliases before checks. Recommendations are limited atomically in DB and cannot span Tools. Withdrawal removes recommendation atomically. Personal API never accepts an arbitrary author ID.

## Frontend/backend contract
Existing catalog item gains `maintainers: RegistryCredit[]` and `recommendedVersionIds: string[]` (ordered). Keep existing fields/version maintainers for backwards-compatible API consumers.

`GET v2/me/contributions?section=original|update|maintained&page=N` (web identity only):
`{section, entries, page, hasMore, total, counts:{original,update,maintained}}`.
Entries are discriminated unions: `{kind:'submission',submission:RegistrySubmissionV2}`, `{kind:'contribution',contribution:Contribution}`, `{kind:'maintained',tool:RegistryItemV2}`. Original/Update lists are one correctly ordered, paginated union, not independently truncated datasets. History includes pending/rejected/published own submissions. Default section original; frontend `section=tools|updates|maintained` maps to the wire values.

`GET v2/catalog/{id}/management`: authorized admin/maintainer only, returns `{item,canAssignMaintainers,maintainers}`. Maintainers is list of `{name,github?,orcid?,url?,contributorId?}`; binding IDs only included for administrator viewers.
`POST v2/catalog/{id}/maintainers`: admin-only `{maintainers:[{name,github?,orcid?,url?,contributorId?}],reason}` replaces public Tool credits and authority bindings, maximum20; allow empty list, valid supported account IDs, reject duplicates.
`POST v2/catalog/{id}/recommendations`: authorized admin/maintainer `{versionIds: string[],reason}` replaces ordered0–2 selection. Return `{updated:boolean}`. Same-Tool checks and withdrawn validation happen server-side.
Existing `POST v2/catalog/{id}/metadata` remains payload-compatible, extends permission to assigned maintainers with in-transaction authorization.
Management GET403 for unrelated accounts,401 for anonymous. Frontend management route `/community/catalog/{id}/manage` preserves login return path. Detail checks management availability using authenticated management endpoint, not public name/handle matching. No authority inferred in browser.

## Rollout and validation
Backend additive SQL migration + least-privilege runtime grants and operator script required. Operator runs owner migration before backend deploy, then frontend; preserve existing tables/IDs/OAuth/session settings. Frontend handles older backend absence safely (no manage links, original display-credit fallback, clear personal/history fallback). Include exact deployment commands and Postman requests with no credentials.
Tests: authorization IDOR/provider identity/revocation/cross-origin; ordinary registrants cannot grant rights; empty/invalid credits; alias resolution; concurrent recommendation limit and wrong/withdrawn versions; withdrawal cleanup; audit/idempotent migration; personal pagination/counts/ownership; Original-only home vs complete detail; inherited maintainer display unaffected by updates; contextual links and sign-in destinations; browser desktop/mobile management and personal sections.

## Builder-check rulings
- Explicit empty Tool-level `maintainers: []` is authoritative; use legacy fallback only when field is absent. Persistent initialization prevents reseeding on migration reruns.
- No central account directory exists. Supported Contributor IDs are numeric GitHub IDs or google/apple colon +64 lowercase hex; no previous contribution/submission is required for admin assignment.
- Management/personal endpoints explicitly reject Authorization headers even alongside a valid web cookie.
- Maintainer replacement returns `{updated:boolean}`. Personal unions sort createdAt descending then stable kind/ID; record entries are published, submission statuses retained.
