# Community governance rollout

This change implements an English, PostgreSQL-backed governance workflow and a service-signed transparency log. It does not enable production by itself. Browser demo accounts and keys are never imported into the production feature.

## Assurance and limits

The backend records real authenticated Community actions, snapshots, reasons, explicit approval votes and candidate acceptance. Signatures attest what this service recorded. They are not personal user signatures and do not establish independent witness operation or blockchain consensus. The public UI states those limits.

The log retains full public event bodies, SHA-256 hash links, Ed25519 service signatures, RFC 9162 style Merkle inclusion paths and chained signed checkpoints. The runtime role cannot update/delete history. A database owner can change schema/roles; independently retained trust roots and checkpoints are necessary to detect an operator replacing history. Do not claim platform-operator resistance before real independent witnesses, monitors and strong user confirmations are deployed.

Each event's state hashes refer to its Tool governance projection; checkpoint `stateHash` is the latest event's resulting projection hash, not a global catalog database root. Full-history verification checks supplied history and signatures; without a separately retained latest checkpoint it cannot detect a server presenting an older otherwise valid prefix. Business authorization is enforced by tested backend transitions; the browser cryptographic check does not independently replay every business rule.

The current publisher authenticates/rebuilds the full retained event tree on each append, and evidence exports contain full history. This favors reviewable correctness for initial traffic; benchmark and replace it with incremental tree/proof storage before large-scale ingestion. Key rotation and trust-root recovery require an explicit reviewed migration and independent re-pinning; changing environment variables is rejected once a log identity is established.

## Prepare keys and schema

1. Review and deploy backend branch `codex/community-governance` with `COMMUNITY_GOVERNANCE_ENABLED=0`. Keep database/OAuth/session settings unchanged. The frontend receives only `COMMUNITY_SERVICE_URL`; never put signing keys or a database DSN in the website.
2. Run `node scripts/create-governance-keys.mjs /secure/new/governance-directory` on the protected deployment host. The directory must not already exist. Private files use mode 0600 and the directory 0700. Store private material in the deployment secret facility; retain encrypted recovery backups separately. Publish `trust.json` through an independently controlled channel and pin its log ID, key IDs and public keys before activation.
3. Set `COMMUNITY_MIGRATION_DATABASE_URL` privately to the migration owner's DSN and run `python3 scripts/apply-governance.py`. It applies `db/005-community-governance.sql` after migrations 001–004. Set `COMMUNITY_RUNTIME_ROLE` to the existing non-owner runtime role when different from `community_runtime`. Do not run the application as the database owner. Existing credits, bindings, versions, accounts and sessions remain intact.
4. Configure `COMMUNITY_GOVERNANCE_LOG_ID`, `COMMUNITY_GOVERNANCE_KEY_ID`, `COMMUNITY_GOVERNANCE_PRIVATE_KEY` from the generated trust/key files. Configure the separate `COMMUNITY_GOVERNANCE_EMERGENCY_KEY_ID` and `COMMUNITY_GOVERNANCE_EMERGENCY_PRIVATE_KEY` before initializing the log. PEMs accept literal `\n` escapes, like the existing Apple key configuration. Set the operation-scoped `COMMUNITY_GOVERNANCE_PUBLISH_TOKEN` from its protected token file. Never expose that credential through the frontend proxy.
5. Enable `COMMUNITY_GOVERNANCE_ENABLED=1`, restart the backend, and run `COMMUNITY_GOVERNANCE_API_ORIGIN=https://your-api-origin node scripts/bootstrap-governance.mjs`. Perform this in the rollout window before opening the new frontend. It records the current members as an explicitly observed baseline, without inventing historical grants. New Tool publication initializes its own baseline. Verify all existing tools initialize successfully; emergency recovery assumes a recorded baseline and registered receipt trust root.
6. Schedule `node scripts/publish-governance.mjs` at least once per minute with the private API origin/token environment. The operation can only publish already authorized, signed pending restriction receipts. Retry failures and alert on nonzero exit. Normal governance commands also drain the queue before granting new authority. Server/OS scheduling itself is not configured by this code change.
7. Deploy the paired frontend and verify anonymous history/evidence access, a real invitation accepted by its candidate, a strict-majority handoff, revoked-session rejection, fixed-version recommendation and outage recovery using designated test accounts. Verify a downloaded package with an independently retained trust configuration and known checkpoint.

## Permission and publication rules

Administrators can invite maintainers globally, set an independent administrator pick, and immediately revoke access with a public reason. Team maintainers can propose additions, their own handoff or removal of an existing member. Proposing explicitly records the proposer's yes vote. The snapshot threshold is floor(N/2)+1, each subject gets one vote, and candidates cannot vote themselves in. Additions/handoffs require candidate acceptance. Membership changes permanently supersede old proposals; the seven-day validity window is checked again on every command and healthy publisher reads append expiry events. The last maintainer cannot simply leave.

Targets distinguish an entire registered repository from a specific published version/commit. Future commits do not inherit approval of a fixed version. Administrator picks are distinct from team recommendations. Withdrawal clears fixed-version recommendations. External repository refreshes and upstream code ancestry are observations from their source, not user-approved changes established by this log.

Web sessions and same-origin checks remain mandatory for governance writes; desktop bearer tokens cannot administer a Tool. Internal provider identifiers are retained only in private account-binding tables. Public records use stable actor digests and explicitly public display credits. Private submission drafts/rejections do not enter the public governance log. Public field validation rejects email addresses and recognizable credentials in newly entered public reasons/names. Existing Registry display credits remain public data; audit projection allowlists remove private account bindings rather than dumping raw audit rows.

Ordinary mutations and their signed checkpoints commit in the same transaction. A signing/proof failure rolls back the business change. Commands use request IDs, content digests and expected versions; retries reuse the original result and stale/conflicting writes return 409. Existing Registry metadata/publication/withdrawal/credit paths are included in the log; their legacy endpoints retain their existing payload semantics. They do not gain the new command API's client-supplied optimistic version guard. Review of a submission must be independent of its submitter; assigned maintainers can review Updates for their own Tool, while new Tool publication remains administrative.

Emergency revocation uses a separate transaction: it records a signed receipt and removes access before attempting ordinary log publication. If publication fails, the restriction remains enforced, the public Tool response exposes pending receipts, and ordinary grants/recommendations are paused until recovery publishes them. Keep the emergency key in a separate signing facility in deployment. If both configured signing facilities or the database are unavailable, the service cannot commit an authenticated restriction; use the operator incident process. Existing history and evidence remain readable when the primary private key is missing. Receipt recovery authenticates the separately registered emergency public key using its main-service-signed registration; it does not require bringing the emergency private key back online. Receipt insertion order, rather than clocks, controls publication order. Deactivating the feature after a log exists does not permit legacy unlogged public writes.

Operator changes to the Registry administrator SQL allowlist are observed and published before the next administrative governance action; this snapshot is labeled as observed, not an original signed administrator-grant event. Real-time audited global administrator/key-policy governance and independent projection monitors remain a subsequent control-plane deployment requirement. Restrict direct owner SQL access and retain the existing private Registry audit as well.

## Rollback and recovery

Pause ordinary publication while retaining the public reader and registered trust configuration. Restore the same protected keys/IDs; never replace them with freshly generated keys for an existing log. Retain history, private binding data, pending receipts and command replay records in backups. Do not run the old destructive catalog reset/import procedures after governance activation without a reviewed migration that preserves the log and reconciles the projection. Rolling back to application code that predates governance removes its protections; use the current compatibility reader/paused writer instead.

No production database migration, key provisioning, scheduler installation, frontend deployment or backend deployment has been run by this implementation task.

## Development verification

- `npm run test:governance` runs pure crypto/policy tests; local API cases skip without a disposable owner URL.
- `COMMUNITY_GOVERNANCE_TEST_OWNER_URL=postgresql://test_owner@127.0.0.1:54339/postgres npm run test:governance` creates and removes a separate test database and API. Never point it at production; only loopback PostgreSQL origins are accepted.
- `python3 scripts/test-community-login.py` runs existing isolated Registry/login/bounty/import/maintenance regressions (PyYAML and local PostgreSQL tools required).
- `npx tsc --noEmit --incremental false` and `npm run build` verify the backend. The paired website adds `npm run test:governance` plus existing Registry suites.
