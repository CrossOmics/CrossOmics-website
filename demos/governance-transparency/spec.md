# CrossOmics 治理权限与公开透明日志 Spec

配套演示：[打开私有 Demo](https://crossomics-governance-demo.fantasticode32.chatgpt.site)。所有账户、签名密钥与见证均为浏览器内模拟。

## 目标与信任边界

状态：评审稿 0.2；日期：2026年11月21日。范围：CrossOmics Community 的超级管理员、Tool maintainer 治理、公开事件发布与可独立验证历史。演示只实现交互和本地验证，不修改现有生产权限。

系统必须让公众知道谁在什么权限和审批依据下修改了什么，并能验证记录自公开检查点之后没有被静默替换。目标是透明、可验证和篡改可发现；不承诺阻止所有已授权恶意决策，也不把平台签名当作用户本人同意的证明。

威胁包括：管理员越权、账户冒用、绕过应用直接改数据库、重写或截断历史、向不同访客展示分叉历史、隐藏尚未发布的权限变更。哈希解决内容完整性；行为者签名与授权重放解决操作归属和规则执行；独立见证与监视器约束日志运营方。所有控制方合谋、客户端或用户设备失陷、服务不可用，仍是明确信任边界。

当前 Tool 页面、Registry v2 提交及管理流程继续使用。第一版按 Tool ID 授权，不引入 Repository 级维护角色；社区权限不授予 GitHub 仓库写权限。

## 角色与权限

| 能力 | 超级管理员 | 被授权 Tool 的 maintainer | 普通账户与公众 |
| --- | --- | --- | --- |
| Tool 资料维护 | 全站；记录公开理由 | 仅自己的 Tool，可直接修改可恢复资料 | 提交修改建议 |
| 新 Tool 审核 | 批准或拒绝 | 提供意见 | 提交注册 |
| 已有 Tool 的 Update 审核 | 可以审核；不能独自批准自己的提交 | 仅自己维护的 Tool；不能独自批准自己的提交 | 提交 Update |
| 发布与撤回 | 普通操作独立复核；紧急情况可有理由地直接限制 | 需另一位合格 maintainer 或管理员复核 | 查看公开历史 |
| 推荐 | 管理独立的管理员精选与普通推荐 | 设置维护团队推荐；不覆盖管理员精选 | 查看推荐来源与版本 |
| 成员增删与交接 | 可直接介入，需强身份确认及公开理由 | 通过成员治理流程 | 接受发给本人的邀请 |
| 全站管理员与治理规则 | 特殊治理流程及独立复核，不允许普通 maintainer 接口修改 | 无权 | 查看公开变更 |
| 其他 Tool 与历史记录 | 所有变更也须留痕，不能无痕重写 | 无权管理其他 Tool，不能删除历史 | 下载验证公开证据 |

授权绑定内部账户主体与 Tool ID；公开日志使用稳定的公开账户标识。GitHub 名称、作者署名、提交记录和公开维护者简介不自动产生权限。不同登录提供方只有在经过明确账户绑定后才能合并为同一投票主体。

所有判断由后端完成，每次修改都重新验证当前授权和资源范围；前端隐藏按钮仅改善体验。撤权后旧会话、已打开的页面和未完成提案不得继续使用失效权限。

## 团队治理和审批流程

### 成员治理

两名及以上有效 maintainer 的成员增删或替换，门槛为 floor(N/2)+1，N 来自提案创建时的成员快照。提案者的一票必须明确记录，不隐式计票；每个主体仅一票。新候选人不能对自己加入的提案投票，未回复不视为赞成。两人需两票，三人需两票，五人需三票。

提案默认有效期七天。管理员可以跳过团队投票直接发出邀请，但不能跳过候选人接受。通过后，新增或继任者仍需本人接受；接受并完成公开发布前不授予权限。单人团队可提名继任者，由对方接受后完成交接。普通成员可退出，但最后一名 maintainer 必须先交接，或由超级管理员公开接管；不能直接将团队留空。

成员和策略使用单调递增的版本号。成员集合或权限策略变化时，尚未生效的提案永久标记为 superseded，必须重新收集审批；即使成员名单后来恢复原样，也不能复用旧票。批准与候选人接受均在生效前再校验成员版本，避免并发变更和失效审批。双人僵局、无人回应及长期失联交由管理员处理，保留原提案及介入理由。

### 内容发布与紧急限制

Update 发布和版本撤回需要一名独立审核者，且审核者不得与提交者为同一账户主体。单人维护团队由管理员复核；管理员自己的提交也不能由本人单独批准。推荐、普通元数据编辑不必逐次表决，但必须公开留痕。

紧急撤权、临时隐藏危险版本属于只减权或限制操作，可在日志发布故障时立即执行。系统必须生成签名紧急收据并写入持久队列，公开显示待补日志状态并告警；恢复后追加完整事件。此例外不能授予权限、发布新版本或提升推荐。

管理员精选与维护团队推荐分开保存。推荐对象明确区分 repository 与 version；版本推荐绑定 commit digest，仓库后续更新不自动获得对特定版本的认可。

## 公开事件与发布状态

### 事件范围与隐私

必须公开的治理事件：管理员角色授予撤销、maintainer 任命移除交接退出、提案与有效投票、Tool 和 Update 发布撤回恢复、推荐和管理员精选变更、公开资料和署名更正、治理规则调整及影响公共目录的同步批次。拒绝的越权请求保留在受限安全日志中，不伪装成成功的治理事件。

草稿、邮箱、登录令牌、私密申诉附件、邀请链接和签名私钥不得进入不可变公开日志。公开理由必须经过敏感信息检查；敏感附件放在访问受限的证据库。需要公开承诺时使用带随机盐的承诺，避免对低熵隐私数据只做普通哈希。

### 发布一致性

状态流：draft → proposed → approved → logged → witnessed → published/effective。rejected、expired、superseded 也是追加事件。投票与提案的“公开”不等于其请求的权限已生效。

提交使用 idempotency key、资源 expected version 和已签名操作摘要。后端在事务中验证权限、审批和版本，写入事件意图与 outbox。序列器按顺序校验、追加日志；只有检查点签名及见证门槛满足后，普通授权、推荐和版本发布才对公开投影生效。不得把数据库本地提交描述为已经完成独立见证。

第一阶段发布目标为正常情况下60秒内可验证公开；未达到时显示具体 pending 状态并保留可查询收据。重试不得产生重复事件。网站、API 和数据下载均携带同一 release_id、checkpoint 与 state hash，客户端遇到旧检查点必须显示落后状态。页面和搜索索引是日志状态的投影，可从日志重建；监视器负责发现数据库投影与日志重放结果不一致。

撤销、更正、恢复通过新事件实现，保留原事件及引用关系。对外部引用、活跃度及引用次数的自动同步，以有来源和采集时间的版本化批次发布，不在页面读取时悄悄覆盖已发布快照。

## 数据结构与密码学验证

### 事件信封

每条公开事件包含 schema_version、log_id、event_id、全局 sequence、Tool 与对象固定 ID、action、公开 actor ID 与 key ID、policy_version、proposal 与审批引用、记录时间、生效状态、公开 reason、修改前后内容或可获取的版本化对象、before_state_hash、after_state_hash、previous_event_hash 及 idempotency 引用。不能只存摘要而丢失原文。时间字段区分行为者声明时间、服务器观察时间和外部见证时间。

严格定义 JCS 规范化 JSON 的输入类型，拒绝重复键、非有限数值和不兼容编码。actor_signature 对含对象、操作、nonce、策略版本和有效期的规范化操作意图签名；event_hash 对不含其自身及派生签名的事件正文做带域分离的 SHA-256。日志叶子提交完整公开信封，包括摘要和签名。不同用途的签名及哈希使用不同域，避免跨协议复用。

### 日志与证据

采用 RFC 9162 风格 Merkle 树：叶子 Hash(0x00 || entry)，内部节点 Hash(0x01 || left || right)，定义空树和非二次幂树的处理。每个签名检查点至少包含 log_id、tree_size、root_hash、state_root_hash、schema/policy/trust 配置版本、签名 key ID、观察时间与前序检查点引用。

公开证据包包含事件原文、包含证明、日志签名检查点、检查点之间的一致性证明、见证签名和公开验证材料。生产实现使用经过测试的透明日志实现和紧凑一致性证明，避免自行实现未经审计的密码学协议。业务监视器额外验证审批门槛、账户范围和状态迁移；见证签名本身不证明一项业务决定正确。

验证器必须使用从可信独立渠道固定的根公钥与日志身份，不能把证据包里自带的任意公钥当作信任根。验证顺序覆盖规范化、事件摘要和顺序、行为者证明、审批和规则、Merkle 包含性、检查点签名、追加一致性、见证门槛、已知检查点的新鲜度及状态重放。

## 独立见证与密钥治理

生产部署建议以三个不同管理域的见证为初始拓扑，客户端要求至少两个签名。此门槛不单独保证所有分叉都不可产生；安全还依赖见证诚实假设、可交叠验证策略、检查点交换和独立监视器。见证必须持久保存最后确认的检查点，只为追加一致的新检查点签名，并拒绝同一树大小的不同根。

网站和日志运营方不能同时控制全部见证。定期在独立存储发布检查点和证据镜像，监视器交换检查点、发现分叉、回滚和长时间不发布。公链锚定可作为后续增强，只承诺已锚定批次存在于某个时间界限之前，不能单独证明业务真实性、原文可用性或实时最终性。

日志签名密钥、用户操作密钥与见证密钥分离。日志密钥使用受保护的服务端密钥设施；高影响用户操作采用绑定摘要的 WebAuthn 或等价强确认，不能将普通服务端代签称为用户签名。密钥注册、轮换、撤销和恢复均有版本化的信任配置及独立审批。轮换不能只靠一条由已失陷旧密钥自我批准的日志记录建立新信任。

必须定义见证离线、日志不可用、签名密钥疑似泄漏和分叉告警时的状态：暂停普通增权和发布，允许留有紧急收据的限制操作，并保留最后可信发布状态。

## 接口和页面

### 读写接口

公开读取：GET /governance/events 支持 Tool、事件类型、actor 与 cursor；GET /governance/events/{id} 返回公开原文及证明；GET /governance/checkpoints/latest；GET /governance/consistency；GET /governance/releases/{id}；GET /governance/trust-config。所有公开数据支持分页和证据包下载。

经过身份验证的命令接口：POST /tools/{id}/governance/proposals、POST /proposals/{id}/votes、POST /proposals/{id}/accept、POST /tools/{id}/recommendations、POST /admin/tools/{id}/maintainers。实际实现沿用现有 Community API 版本前缀；这些是语义接口草案。写入必须携带幂等键、资源版本与必要的操作签名，返回 event/proposal ID、receipt 和真实发布状态。

### 页面体验

公开日志：按时间浏览，选择一条事件查看修改前后、操作者、依据、发布状态及验证入口。团队与权限：展示当前成员、邀请与交接状态，按真实后端能力显示操作。提案与表决：展示快照成员、门槛、有效票和候选人确认。验证台：下载原文与证明，分别显示完整性、身份、规则、收录、一致性、见证与新鲜度结果。

普通公众无需登录即可读取和验证。任何“验证通过”必须说明验证范围及信任根；不得用单一绿色标记掩盖尚未独立见证或身份未确认。

### 公开浏览与治理 Lineage

正式版在 Community 和每个 Tool 页面提供无需登录的治理记录入口，支持按 Tool、Repository、操作者及提案筛选。每条事件拥有固定 ID 或 Hash 的永久链接，可下载原文、签名、包含证明及检查点。Demo 的事件链接仅适用于当前浏览器会话；刷新或跨会话访问必须明确提示记录不可用，禁止悄悄替换为另一条记录。

治理 Lineage 连接操作当时的有效授权、邀请或提案、有效表决、候选人接受和适用规则。例如：管理员邀请 AAA → AAA 接受 → AAA 推荐 NuSTAR。团队交接后的新推荐还应追溯到交接提案与达到门槛的有效票；依据缺失时显示证据不完整。Hash 链的前序事件仅表示全局顺序，不能替代授权因果关系。历史操作不得使用今天的成员名单解释当时权限。

Repository 与版本 Lineage 单独展示。指定版本推荐连接已签名记录中的固定提交；仓库推荐不自动绑定某次提交或认可未来版本。提交祖先与 fork 关系须依据源仓库或可验证来源，不能由名称推断。事件详情展示相关仓库治理记录、检查点和存证状态；若启用公链批次锚定，提供对应交易链接及该事件属于该批次的包含证明。链上只保存摘要时，完整事件和证据仍必须公开保存。

当前 Demo 提供可点击的治理依赖视图、证据验证、固定提交链接及源仓库历史入口。它仍为私有的浏览器原型，没有共享持久日志、真实公链交易、生产身份认证或独立运营见证。

## 验收标准与实施阶段

### 必须通过的验收

- STAR maintainer 不能修改 BWA；公开署名不产生管理权；撤权在下一次请求即失效。
- 重复投票、候选人提前投票、失效成员快照、自我审核和未接受邀请均不能使授权生效。
- 同一幂等请求只产生一次业务生效；并发成员变更不会复用过期审批。
- 修改原文、删除记录、截断末尾、调换顺序、伪造签名、替换包内公钥、缺少见证、提供陈旧或分叉检查点，验证器必须拒绝或明确降级。
- 日志无法发布时，普通增权保持 pending；紧急减权有签名收据、告警和补记，不丢记录。
- 页面和导出数据可重放到同一 state hash；推荐绑定对象不会随远端 HEAD 静默漂移。
- 更正保留原记录；公开数据中无令牌、邮箱或私密附件；桌面、移动端、键盘和屏幕阅读器可完成关键流程。

### 实施阶段

P0：确认权限策略、公开字段、信任根与独立见证运营责任，完成威胁模型和接口契约。P1：事件命令、事务 outbox、确定性投影、追加日志、签名检查点、公开历史、验证器和原文备份。P2：用户强确认、真实独立见证、检查点交换、监视器和密钥恢复演练。P3：按需求加入公链批次锚定和更多镜像。

P1 可以交付可审计日志，但在 P2 的独立见证与身份确认完成前，界面不得宣称已能约束平台运营方或证明用户本人同意。

## 演示范围与参考资料

Demo 展示：切换模拟账户、超级管理员任命、维护团队推荐、严格过半投票与候选人接受、撤权后的范围限制、公开事件原文、SHA-256 Hash 链、Merkle 包含证明、数字签名、全量历史追加验证、证据包下载，以及修改/截断副本后的验证失败。

全部为演示账户与数据。密钥、日志签名者和两个见证均在同一浏览器生成；它们不是独立运营服务，角色切换也不是实际认证。Demo 的一致性验证采用完整历史重放，不冒充生产版紧凑一致性证明。刷新页面会重置演示；不写入 Community、GitHub 或任何生产权限。证据包自带公钥仅便于检查格式，不能作为独立身份信任来源。
